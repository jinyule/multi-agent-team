## 候选比较

| 候选 | 用户目标 | 平台关联 | 相对复杂度 |
| --- | --- | --- | --- |
| A：外部程序控制接口（已选） | 从桌面平台使用 nano-harness，无须操作终端界面 | 直接支持自建引擎接入 | 中等 |

## A. 外部程序控制接口

### 建议交给团队的一句话目标

让桌面平台能以程序方式使用 nano-harness，提交任务、观察执行、处理审批、中断任务，并恢复已有会话。

### 已有能力与实际缺口

[`main.go` 的命令分发](/opt/code/ai-workspace/nano-harness/cmd/nano-harness/main.go:112)提供 version、help 和 tui，目前没有对应的外部控制命令。内部已存在 Followup、Steer、Interrupt、会话恢复和事件日志；[TUI 同时承担审批交互](/opt/code/ai-workspace/nano-harness/internal/adapter/tui/tui.go:207)。

新增点是提供可被桌面平台消费的产品接口，复用现有 agent 能力和事件事实。具体选择 stdio、其他本地传输或标准协议，应在方案阶段比较，不在候选选择时锁定。

### 建议首轮范围

- 聚焦本机、单执行进程和单根会话。
- 支持创建或恢复会话、提交输入、接收执行进度与结果、中断活动工作。
- 把审批请求交给调用方，并接收关联到具体请求的明确决定。
- 约定错误、连接关闭、执行结束和恢复的行为。
- 复用已有账户配置；完整账户登录 UI、多客户端共享控制和远程服务不作为这一候选的必需范围。
- 保持现有审批语义，不因增加接口就自动允许写操作。

### 建议功能验收

1. 独立测试客户端通过选定接口启动真实 binary 并提交任务。
2. 使用确定性 loopback provider，经过真实模型协议解析、工具执行和持久化链，返回可核对的结果。
3. 客户端收到工具审批请求；拒绝时没有对应写入，明确允许时才发生预期变化。
4. 执行中断后停止活动工作并完成资源清理；重启恢复时历史仍可核对。
5. 非法请求、无效审批关联、客户端断开和输出失败具有明确结果。
6. 原有 TUI 路径与既有门禁仍通过。

### 能检验平台什么

产品成员需要澄清外部调用者的真实需求；架构成员比较接口和生命周期方案；开发与测试成员完成跨层实现；独立评审者检查边界和证据；最终产物可以直接帮助平台接入 nano-harness。

可先由平台已接入的现有编程 Agent 完成该任务，再接入 nano-harness，避免把尚未实现的接口作为首个任务的前提。

## B. 子 Agent 受控开发权限

### 建议交给团队的一句话目标

允许子 Agent 在用户明确授权的工作范围内修改文件和运行测试，同时保留越界拒绝、撤销和可追溯记录。

### 已有能力与实际缺口

[架构规则](/opt/code/ai-workspace/nano-harness/docs/architecture.md:150)明确把 delegated session 的策略固定为 `never`，子 Agent 不能使用需要审批的写入与 shell 工具。[审批执行路径](/opt/code/ai-workspace/nano-harness/internal/app/approval/service.go:169)对 delegated request 不向审批 broker 请求授权。

这是现有设计边界，不作为缺陷报告。该候选会改变授权模型，需要用户在方案阶段判断新规则，并按仓库要求更新 ADR、安全契约与测试。

### 建议首轮范围

- 先解决一个父任务对一个子任务的受控授权。
- 明确授权者、目标 workspace、允许的能力、授权期限与撤销条件。
- 未授权时保留当前拒绝行为；不能通过修改提示词或放宽全局策略获得权限。
- 任意 host 执行、跨项目授权和自动把权限转授给后代不默认纳入首轮。

### 建议功能验收

1. 未授权子 Agent 仍不能写文件或运行 shell。
2. 被授权子 Agent 能通过真实工具在指定 workspace 完成一项修改和确定性验证。
3. 范围外写入、未允许能力和授权转授被拒绝。
4. 取消、撤销、重启和异常退出后的授权行为有明确契约及测试。
5. 从实际文件、进程结果和会话记录确认行为，不能只断言 Agent 的成功文案。

### 能检验平台什么

尤其适合验证负责人委派、专业角色提出相互独立的意见、重大边界交给人判断，以及允许/拒绝路径都需要测试的质量流程。相较 A，涉及更多授权与恢复规则，不建议通过简单增加“全部允许”开关实现。

## C. 会话检索与执行报告

### 建议交给团队的一句话目标

让我找到过去的一项任务，并导出可检查的执行报告，了解它完成了什么、执行过哪些动作、哪些事情被拒绝或中断。

### 已有能力与实际缺口

[`transcript.Repository`](/opt/code/ai-workspace/nano-harness/internal/app/transcript/transcript.go:29)已有 List 和 Inspect；[JSONL adapter](/opt/code/ai-workspace/nano-harness/internal/adapter/session/jsonl/jsonl.go:195)实现只读检查。当前命令入口没有将这些能力暴露为会话查找或报告导出功能。

新增点是可供用户和平台使用的检索及报告能力，而不是重新实现持久化系统。

### 建议首轮范围

- 提供有界的会话列表和必要筛选条件；具体检索维度由产品方案决定。
- 选择一个会话，导出结果、工具执行、审批、异常或中断状态，以及指向原始事件的引用。
- 报告从现有持久化事实确定性生成，首轮不依赖额外模型总结。
- 明确报告中原始内容、文件正文和敏感信息的展示策略。
- 原始会话保持只读，不在导出过程中修改或修复日志。

### 建议功能验收

1. 用真实会话文件验证列表、筛选、无结果和边界行为。
2. 已完成、失败、拒绝和中断任务被准确区分，不能一律展示为成功。
3. 工具请求与结果、审批请求与决定的引用可回到对应事件。
4. 损坏或不支持的日志有明确错误；读取和导出不改变原始文件。
5. 通过真实 binary 导出报告，再由独立测试读取文件核对内容。

### 能检验平台什么

适合检验产品角色定义“人需要看什么证据”、测试与评审角色纠正报告遗漏，以及从真实 CLI 到最终文件的完整验收。对多 Agent 委派和交互控制的覆盖弱于 A、B。

## 共用的平台验收要求

以上任一候选都要同时经过拟建平台的交付流程：

- 将一句话目标变成具体方案和验收标准；方向不明确时先交给用户判断。
- 保留新增行为的有效 TDD 红灯与绿灯证据及代码版本。
- 执行适用的单元、集成、E2E 与 nano-harness 仓库门禁。
- 由非作者成员独立检视，处理反馈并重新验证。
- 创建 PR，修复 CI 问题，用户最终确认后才能合入主干。
- 准备对应版本的发布说明和已验证构建产物，由用户决定发布。
- 记录人工介入、总耗时和资源使用，验证是否减少了用户的协调负担。

功能测试验证 nano-harness 的新增能力；以上交付记录验证多 Agent 平台自身是否履行职责。两者需分别验收。
