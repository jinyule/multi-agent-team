# ADR-001：独立桌面与本机任务服务

日期：2026-09-12。状态：已接受。决策者：用户。依据：用户明确回复“好，那就方案二”。

## 决定

采用方案二：独立桌面工作台通过本地接口连接常驻任务服务；服务拥有持久业务状态、执行管理和交付控制。桌面退出不等于停止团队；电脑停止运行时本机任务无法继续。

首版业务服务采用模块化单体。固定成员身份与引擎解耦，负责人提出计划，程序执行预算、权限和质量约束。等待人的任务不阻塞不相关工作。每次合入主干、实际发布分别保留人的决定。

## 工程默认，非额外的用户确认

- 桌面：Electron、React、TypeScript；服务：Go；持久化：SQLite 与本地文件。
- 首个开发环境按当前 Apple Silicon macOS，同机部署；服务使用 Unix socket，保留未来其他传输适配边界。
- 服务初期通过独立命令启动。系统登录启动、安装器与签名在分发阶段实现；不自动修改用户系统服务配置。
- 第一阶段只落地项目、目标、团队与持久事件，以及独立服务和桌面连接。未接引擎前，目标保持“等待引擎接入”，不生成虚构执行结果。

用户随后确认：**首版支持 macOS，桌面和任务服务都在本机；首轮同时接入 Codex 与 Claude Code**。nano-harness 在外部控制接口完成后接入。远端执行不属于这次选择。

## 原因与代价

独立服务使任务生命周期不依赖聊天窗口，适合个人持续使用；相较成熟工作流服务器，首版基础设施较少。代价是自己实现有限的持久调度与故障核对，并管理服务升级与恢复。实现范围、故障验证与退出条件见[实施设计](../architecture.md)。

方案一和三保留为历史比较。若后续多机长流程的恢复成本明显上升，可以重新决策，不能视为无成本切换。
