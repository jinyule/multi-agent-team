# 人机协作多 Agent 编程平台：需求访谈草案

更新日期：2026-09-12。

本文件记录访谈结论。标注为“已确认”的内容来自用户直接表述或选项回答；“推导建议”用于把要求变成可实现、可验收的行为；“待澄清”尚未形成决定。当前进入平台详细设计与基础实现阶段，nano-harness 尚未修改。

架构讨论已整理为[三个架构方案](architecture-options.md)。**用户已选定方案二：桌面 + 本机常驻任务服务**，决定见 [ADR-001](adr/001-local-service.md)。未单独确认的实现细节仍区分为工程默认与待澄清事项。

## 1. 产品定位：已确认

面向用户个人的桌面应用。用户长期带领一支按专业分工的固定 Agent 团队，在本机完成编程项目从需求澄清到可发布版本的工作。

用户负责方向、判断力、口味和最终验收。团队承担需求细化、验收标准制定、任务拆解、开发、测试、交叉检视、修改和交付准备，尽量减少过程中的人工介入。

首版同时允许接入已有编程 Agent 的执行能力，以及 nano-harness 等自建引擎。nano-harness 已确定作为首版验收的示例项目；用户已选择“外部程序控制接口”作为具体新功能，接口契约待方案确认。

### 首版边界

| 维度 | 已确认的选择 |
| --- | --- |
| 真人使用者 | 先服务用户个人 |
| 产品形式 | 独立桌面应用 |
| 执行位置 | 先在用户开发机上执行 |
| 首发系统 | macOS，桌面和任务服务同机运行 |
| 团队 | 长期固定成员，按专业分工 |
| 统筹 | 一名固定的团队负责人 |
| 引擎 | 现有编程 Agent 与自建引擎两类均可接入 |
| 首轮现有引擎 | 同时接入 Codex 与 Claude Code；nano-harness 控制接口完成后接入 |
| 工作并行 | 负责人按依赖、优先级和资源额度自动安排 |
| 最终交付 | 版本、发布说明和验证过的构建产物已准备好 |
| 发布决定 | 由用户决定是否发布 |

多人组织协作、远程执行和自动生产部署尚不是首版已确认的交付要求。

## 2. 人与团队的决策边界：已确认

人的主要参与节点如下：

1. **方向或口味不明确**：团队先调查，准备具体方案、取舍和必要的小原型，请用户判断后继续。不能把“尽量不在回路”解释为自行决定所有尚不明确的产品方向。
2. **每次合入主干之前**：本地门禁、Agent 交叉检视和 PR CI 通过，相关问题已修复，再交给用户最终 review。用户主要审成果、测试证据、风险和关键取舍，必要时下钻代码。
3. **准备发布之后**：交付可发布版本，用户决定是否实际发布。

以下例外也需要人的判断：

- Agent 分歧经过举证、讨论和验证仍不能解决。
- 需要放宽已定验收标准、降低质量要求、删减范围或绕过门禁。
- 需要超过用户授权的总资源预算，或改变重要交付承诺。
- 建议开展超出用户既定目标范围的新工作。

团队应带着具体选项、证据、影响和建议提出问题，而不是把未处理的困难直接转交给用户。

## 3. 团队组织：已确认及待细化

已讨论的固定角色包括：团队负责人、产品、架构、开发、测试和代码评审。

- 团队负责人负责协调、跟进交接、处理阻塞和推动收尾。
- 专业成员承担各自职责，保留长期身份和合作经验。
- 用户可以直接与任意成员交流，不必所有沟通都经过负责人。
- 变更作者不能批准自己的变更；评审由另一名成员独立完成。
- 不强制使用不同模型完成交叉检视。

**待细化**：每种角色的数量、是否允许兼任、验收测试与单元测试的编写分工、评审通过的判定规则、负责人可以自行裁决的具体事项。

## 4. 开发和交付流程：已确认

```text
用户提出目标
  → 团队澄清需求、调查并准备方案
  → 方向不明确时，由用户判断
  → 细化需求、制定验收标准、拆分任务
  → 按依赖与优先级安排执行
  → TDD 开发与持续验证
  → 单元测试、集成测试、E2E 及项目质量门禁
  → 独立成员交叉检视
  → 修改并重新验证，直至可交付
  → 推送分支、创建 PR
  → GitHub / Gitea CI 门禁及失败修复
  → 用户最终 review、确认合并
  → 准备可发布版本、发布说明和验证过的构建产物
  → 用户决定是否发布
```

流程中允许团队按需返回调查、需求细化、开发和验证阶段，但不能自行放宽已定质量要求。上图表达产品行为，不预先指定工作流框架或任务调度实现。

GitHub / Gitea 均出现在用户期望的托管与 CI 场景中；首版具体适配范围和顺序待定。

## 5. 质量要求：已确认

### TDD

- 新增行为和缺陷修复必须保留“测试先失败、实现后通过”的证据。
- 证据记录对应代码版本。
- 纯文档或机械修改按适用规则处理。

### 门禁与检视

- 单元测试、集成测试、E2E 和代码检视是质量流程的一部分。
- Agent 在提交用户最终 review 之前，先自行消除测试、检视和 CI 暴露的问题。
- PR CI 通过后才进入人工最终验收；每次合入主干仍需用户确认。
- 评审者独立检查需求、代码和验证证据，不以作者自述的成功作为评审结论。
- 团队可补充测试、加强验收标准；放宽已定要求必须升级给用户。

### 项目现状，仅作为参考

已只读查看 nano-harness 的 `AGENTS.md`、`Makefile`、`docs/testing.md` 和 `.github/workflows/ci.yml`。其中定义了本地 `make check`、race、逐产品源文件覆盖率、真实入口验证，以及 CI 汇总等检查。本次访谈没有运行这些检查，也没有验证线上分支保护配置。

该仓库的具体阈值不自动成为所有项目的通用平台政策。

## 6. 日常交互：已确认

以下三个入口同时保留：

1. 与团队负责人沟通和推进工作。
2. 在共享群聊中直接与专业成员讨论、指定方向和提出修改。
3. 通过项目、任务和成果视图查看进度与产出。

默认首页优先展示需要用户判断的事项和成果，包括方向选择、合并确认和发布决定；各事项附可供判断的方案、证据和建议。

**推导建议**：三个入口操作同一份任务状态和决策记录。用户在任何入口确认的方向应能被相关成员获得，避免重复解释或出现相互矛盾的执行要求。

## 7. 自主执行、预算和范围：已确认

- 用户设置项目或周期的总预算及并发上限。
- 负责人在总授权内估算、分配和调整任务额度。
- 团队可以在授权范围内调查失败、切换方法、调整参与成员并重试。
- 超出总授权或涉及重要交付取舍时，整理材料交给用户判断。
- 同时存在多个需求时，负责人自动处理依赖、优先级和并行安排。
- 实现既定目标所必需的补充工作可以自主纳入。
- 范围外的改进进入建议清单，不直接扩大开发范围。

**待细化**：预算采用哪些计量单位、周期长度、默认并发上限、各引擎用量不可获取时的处理，以及暂停任务后何时允许恢复。

## 8. 方向与口味的积累：已确认

- 明确的长期要求自动记住，按适用的个人或项目范围用于后续任务。
- 明确只针对本次的意见仅作用于本次。
- 推断出的偏好作为候选，确认前不直接变成长期规则。
- 团队利用已确认的方向和偏好，减少同类问题反复询问。

**待细化**：成员经验与团队共享经验的关系；记忆的查看、纠正与撤销方式；规则冲突和失效如何处理。

## 9. 推导建议，尚非全部已确认要求

以下建议使上述目标可执行、可检查，仍需在需求评审时定稿：

- 测试和评审结论绑定具体代码版本；后续变更使受影响的检查失效，需要重新验证。
- TDD 的失败证据应证明目标行为缺失或缺陷存在，不能用无关环境故障冒充有效的红灯。
- 每项工作记录负责人、输入、验收标准、依赖、产物、证据和决策。
- 并行任务采用适当的代码隔离与集成验证，避免分别通过的成果合在一起后失败。
- 正在等待人的任务与可以继续推进的独立任务分别处理，避免一处等待阻塞全部工作。
- 固定成员身份与具体模型、执行引擎解耦，使成员切换引擎后能够延续工作经验。
- 合并后的验证与发布产物对应实际将要发布的代码版本。

这些建议不预先指定数据库、协议、消息队列、Git 隔离方式或具体技术栈。

## 10. 首版验收场景

**已确认**：以 nano-harness 的一个真实新功能完成全流程验收，而不是只演示多个 Agent 对话。

**具体功能（已选）**：外部程序控制接口——让桌面平台能以程序方式使用 nano-harness，提交任务、观察执行、处理审批、中断任务，并恢复已有会话。

用户从三个基于当前代码提出的候选中选择了该功能；“子 Agent 受控开发权限”和“会话检索与执行报告”保留为参考，不自动进入首版范围。具体接口协议、生命周期、权限传递和验收细则待方案讨论。详见[验收功能候选与已选场景](nano-harness-acceptance-candidates.md)。

该选择只确定平台验收场景。本次仍处于产品设计讨论阶段，没有开始实现 nano-harness 功能。

建议对这个案例记录：

- 团队从模糊目标形成了哪些方案、需求和验收标准。
- 用户参与了哪些判断，是否出现可以避免的重复解释和催办。
- TDD、单元/集成/E2E、独立检视和 CI 的实际证据。
- 失败、分歧、返工和预算分配是否按约定处理。
- 最终功能是否符合已定方向，以及产物是否达到可发布状态。
- 人工投入时间、总交付时间和实际资源消耗。

成功率、人工投入、时间和成本的具体阈值尚未确定；测试通过本身不等于产品验收通过。

## 11. 后续需要作出的具体决定

1. 已选外部控制接口的具体契约、成功标准和资源预算。
2. 专业角色的职责契约，尤其是测试编写、代码检视、整体验收和负责人裁决之间的边界。
3. macOS 同机运行、首轮 Codex 与 Claude Code 已确认；GitHub / Gitea 的具体支持范围待定。
4. 用户修改方向、暂时不答复、拒绝合并时，任务如何暂停、调整与恢复。
5. 执行中断、桌面退出或本机重启后的恢复要求。
6. 需求、决策、成果、版本证据和记忆在桌面界面的具体呈现方式。
